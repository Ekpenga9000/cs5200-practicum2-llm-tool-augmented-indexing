## Methodology Note: Query Workload Generation

The standard TPC-DS query set is normally rendered from its query templates using the benchmark's official `dsqgen` tool. In this environment, `dsqgen` could not be reliably invoked, so the query workload was instead generated with a custom Python template renderer built specifically for this run. This renderer resolves the TPC-DS template substitution language — list expansion (`ulist`), value distributions (`dist`, including table-specific distributions like `fips_county`), arithmetic bounds (e.g., `rowcount(table)/5`), and date interval arithmetic — and was iteratively corrected against real parser and runtime errors from PostgreSQL until all 99 queries executed successfully against the loaded schema.

This approach produces syntactically valid, executable SQL that follows the structure and intent of each TPC-DS template. However, because it is a custom reimplementation rather than the official generator, two limitations should be noted:

1. **Substituted values are not guaranteed to match `dsqgen`'s exact distribution logic.** Where the official tool draws template parameters from precise statistical distributions defined in the TPC-DS specification, this renderer uses simplified approximations (e.g., representative state/county/GMT-offset values for `fips_county` slots). This may affect selectivity and result set sizes for some queries, though it does not affect query structure or validity.
2. **A small number of queries required minor rewrites to run correctly under PostgreSQL**, distinct from the template substitution logic itself:
   - Three queries using a `lochierarchy` alias inside an `ORDER BY CASE` expression were rewritten to repeat the underlying grouping formula, since PostgreSQL does not resolve select-list aliases inside `ORDER BY CASE` the way the original template assumes.
   - One query (the AM/PM sales ratio query) was hardened with `NULLIF` to avoid a legitimate divide-by-zero on this dataset, preserving the intended ratio calculation while preventing a runtime error on months with zero PM transaction counts.

All 99 queries execute successfully and produce real query plans and execution times against the fully loaded and independently row-count-verified TPC-DS (SF1) dataset. Given the time constraints of this submission, the renderer's output was validated by successful execution and the standard full-file empty-scan check (confirming no query returned a stale or wrong-schema empty-scan pattern), rather than a full semantic audit of every rendered query against the TPC-DS specification. This is a disclosed limitation of this deliverable rather than a hidden one; a production research submission would validate rendered query semantics against `dsqgen`'s reference output directly.
