## JOB

JOB shows the largest Tool Benefit magnitude of any benchmark in this study: -390.466 percentage points, driven overwhelmingly by a single query (22d), whose Condition B execution time increased from 1.6 seconds at baseline to approximately 30.8 minutes after the recommended indexes were applied. Because a regression of this size is far outside the range seen in any other benchmark, we treated it as a candidate measurement artifact until it could be independently verified against a live database, rather than accepting the aggregate figure at face value.

**Verification.** Three checks were performed directly against the measured database:

1. _Schema resolution._ The Condition B input for JOB sets `schema_name` to `"postgres"`, which raised a concern that this value — intended as a database name — was being misapplied as a `search_path` schema and could cause queries to silently resolve against the wrong or empty schema. Live inspection confirmed that all three tables referenced by query 22d (`title`, `movie_info`, `cast_info`) were present in the `public` schema, and `search_path` correctly resolved to `public` through the configured fallback. This ruled out schema misconfiguration as a cause.
2. _Database state._ The live database had drifted from its measured state (76 indexes present instead of the 35 recorded for Condition B — 21 primary keys plus 14 recommended indexes), because a later Condition A remeasurement had been run on the same database without first removing Condition B's indexes. The database was restored to the exact 35-index state before further diagnosis.
3. _Query plan._ With the database in its correct measured state, a fresh `EXPLAIN ANALYZE` on query 22d showed that 99.99% of its 1,846,132 ms runtime was spent in a single Nested Loop node. The planner estimated 1 row for this node but the query actually processed 46,281, and the inner side of the loop performed an Index Only Scan on the recommended composite index `(info_type_id, info, movie_id)` — 47,475 times, at roughly 35 ms each. This fresh diagnostic timing differs slightly from the recorded Condition B median of 1,872,844.811 ms because it was a separate execution.

**Root cause.** The regression is real, not an artifact, and it is attributable to a specific, well-understood index design flaw. The recommended index orders its columns as `(info_type_id, info, movie_id)`, but query 22d filters `info` with a range predicate (`info < '8.5'`) while needing `movie_id` — which appears after `info` in the index — for each outer-loop iteration. Because a range condition on a middle column prevents efficient use of any index columns that follow it, each iteration of the nested loop must scan a large portion of the range-matching rows to locate the needed `movie_id`, rather than seeking directly to it. Postgres's planner compounded this by severely underestimating the resulting row count (1 estimated vs. 46,281 actual), which led it to select a nested-loop join that would have been reasonable only if the cardinality estimate had been correct.

**Interpretation.** This is one of the clearest concrete examples in our dataset of _why_ tool-augmented index recommendation can still fail even when the tool itself functions correctly and returns genuine cost estimates. The cost estimator evaluates each candidate index against a query in isolation; it does not model how a candidate index's column ordering interacts with the predicate structure of the query that motivated it — specifically, the standard rule that an index's usefulness for a trailing column collapses once a preceding column is constrained by a range rather than an equality predicate. This is a limitation of the tool's cost-estimation granularity, not of tool access in principle, and it recurs in a milder form in several of the over-indexing patterns observed elsewhere in this study (e.g., TPC-DS Condition A).

We classify JOB's aggregate result as **high confidence**: the extreme value is not a measurement error but a mechanistically explained, reproducible outcome, verified directly against the measured database state.
